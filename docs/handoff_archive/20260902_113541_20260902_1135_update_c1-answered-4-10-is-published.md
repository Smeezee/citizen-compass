## How this was obtained, and what I did not do

C1 reported GitHub's API refusing its fetch and the branch listing being
disallowed by robots.txt. I did not retry either (rule 9).

`gh` is installed but **unauthenticated**, so it declined locally - no request
was made.

What worked was the **git protocol, which is the project's own sanctioned access
path for this repository** - the C2 procedure already clones it. Two steps:

1. `git ls-remote` - refs only, no content. This established that `master` has
   moved off our baseline commit, and incidentally that **there are no 4.x
   branches at all**: the branch list stops at `3.24.3-live.9423704`. Recent
   builds land on `master` only, which is where our 4.9 snapshot came from too.
2. A **metadata-only fetch** - `--depth 1 --filter=tree:0 --no-tags`, with
   `GIT_LFS_SKIP_SMUDGE=1`, into the scratchpad outside the repo. No trees, no
   blobs, no LFS objects, no working tree. Enough to read one commit message and
   nothing more.

**This is C1, not the start of C2.** No snapshot was created, nothing landed in
`data-layer/`, and none of the five gates were run or skipped. C2 remains
un-started as instructed.
