# Update — the tray was slow for a measurable reason, and it is a correctness risk

`rescanAndScore()` + `regenerateHandoff()` ran after **every single inbox file**,
serially. Measured from the watcher's own log: roughly **one file every two to
three minutes**, ~70s of it the rescan.

With ten memos queued that is a tray taking half an hour to drain.

## Why that is not just slow

**Three orders landed on one row today** — publish the RAPTOR as a $50 ship,
remove it, keep it as a labelled joke — each reversing the last. **A slow tray
means acting on an order already withdrawn.** It cost nothing this time only
because the delay outlasted the reversal, which is luck, not design.

## I checked my own suspicion first, and it was WRONG

The log shows the same `96109 chars` after every regeneration, so I assumed the
output was identical and the work redundant. **I hashed the file across a
regeneration before changing anything: the hash CHANGED.** Same length, different
content — the counter increments and the newest update rotates in.

So the regeneration is not wasted and skipping it would lose content. **Only the
REPETITION is waste**: doing it once after a batch says exactly what doing it
nine times says.

Had I not measured, I would have "fixed" it by removing real work.

## The fix, and the two ways it could have been worse than the fault

Defer the rescan while more files are already waiting, then do it once.

    counting the protected subdirs as pending  -> watcher believes it is
                                                  permanently busy and NEVER
                                                  regenerates again
    deferring with no cap                      -> a queue that never empties
                                                  defers forever

**Both fail silently and look like a healthy watcher**, so both are tested.
`pendingInboxFiles()` counts top-level files only; `maxCoalesced = 10` caps the
run so the eleventh file pays regardless.

Mutation-proven: counting directories makes it report 2 pending forever, and the
test names that exact consequence rather than just failing.

Deployed, PID 39296. Old binary moved aside, not deleted.

**The live path has NOT fired yet** — the queue emptied before the new binary
started, so coalescing is unit-tested and not yet observed in place. This update
is one of two files dropped together to exercise it; the log will say
`deferring the rescan` or it will not, and I will report which.
