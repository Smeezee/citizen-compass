# Update — collector2 builds, 30/30 green, and the reader recorded ZERO of 299

Rebuilt from what is on disk (7 files, 1,797 lines). **It had never been
compiled and it did not compile.** Fixed, then found three more defects — one of
them the reason the first real reader was recording nothing at all.

## It did not build: two unrelated pairs both named before/after

`selftest.go` held `before`/`after` as `os.FileInfo` (measuring append-only
growth by bytes) and redeclared the same names as `int` counters in the same
scope. Renamed the counters `believedBefore`/`believedAfter`. Also note
`collector2` is not in `go.work`, so it builds with `GOWORK=off` — the workspace
was left alone rather than edited.

## Defect 1 — a crash mid-write silently ate the NEXT observation too

`store.go`'s `Record` wrote `json + "\n"` under `O_APPEND`. Correct only if the
file already ends in a newline — which is exactly what a crash mid-write does
not leave. The next `Record` landed ON the partial line and made one line that
was neither observation: unparseable, skipped by `Each`, gone with no error.

The file's own header claimed *"a crash mid-write costs the tail of one line and
nothing before it."* True for everything before it. **The line after it was lost
as well, and nothing reported that.** Now opens `O_RDWR` (still `O_APPEND`),
reads the last byte, and closes the broken line before opening its own. The
truncated line stays truncated and stays skipped — inventing the rest of a line
nobody wrote is worse than losing it.

Three assertions failed on this and now pass: the self-test WAS the known-bad
input, so this is proven in both directions.

## Defect 2 — the teaching loop was passing on the wrong answer

`derive.go:119` keys the taught vocabulary on TEXT alone and drops Kind and
Source. So the unknowns section's answer (Quantanium → Quantainium, a `shop_row`
from `kiosk@1`) was already rewriting the `shop_transaction` readings `kiosk@3`
takes 100 lines below. By its first `Derive()`, the correction had happened.

**So "ONE ANSWER REACHED A READING TAKEN BEFORE IT WAS GIVEN" — the assertion
the file calls the whole point of the program — was passing on somebody else's
answer.** The proof sat two lines under it: "REPORTS what moved" said nothing
moved, because the answer under test had nothing left to change.

Fixed in the TEST, not the design: the block now uses a misreading nobody has
answered (Astatinne → Astatine). The global-by-text vocabulary is untouched — it
is defensible and teaching once reaching everywhere is the point — but it is now
ASSERTED by a new check instead of relied on by accident. Mutation-tested:
scoping `lexicon()` by kind fails ONLY that new check and leaves the teaching
headline green.

**30/30 green, `go vet` clean, exits 9.**

## Defect 3 — the reader recorded NONE of the 299 real transactions

`-read` on the live `Game.log` reported 0 observations. That was honest: the
live log holds zero transactions today. But 243 logbackups sit beside it, so I
ran the real `GameLogReader` over all of them (probe gated behind `CC_ARCHIVE=1`,
writing to a temp dir, in `collector2/zz_archive_probe_test.go`).

    BEFORE   243 files -> recorded 312, asked 299   kinds: payout only
    AFTER    243 files -> recorded 601, asked  10   payout 312, shop_transaction 289

`read_gamelog.go` asked for `fields["item"]`, then `fields["name"]`. **The game
writes `itemName`.** Neither key ever matched, so every transaction fell through
to "transaction parsed but names no item". `derive.go`'s PriceRule reads the
same two keys, so even a recorded one would have derived nothing.

I got the line in front of me before touching anything, as instructed. Mapped
the game's words to the program's AT THE READER — `itemName`→`item`,
`client_price`→`price` — so the game-specific dialect stays where this file says
it belongs. The refusal branch is untouched: a line that genuinely names no item
is still a question.

**The 10 that remain are the RIGHT 10.** They carry `resourceGUID` and
`transactionMode[ResourceContainer]` — commodity cargo, which names no item. Q42's
Python miner found exactly 10 commodity rows. The reader is honestly asking about
the same 10 it cannot name.

## Defect 4 — playerId and shopId were being written into the store

The refusal kept the raw line, so `unknown.json` accumulated
`playerId[204354536218] shopId[...] kioskId[...]` for all 299, and those ids also
landed in `fields` on every observation that recorded.

`gamelog-mining/MANIFEST.json` states the standard for the Python miner: *"No
playerId, shopId, session id, shard id, account id or player handle is present in
any output file."* This reader is a second way into the same data.

collector2 has no send path, so nothing left the machine — **but the store is
append-only by design, which means an id written now is an id nobody can take
out later.** That is the argument for fixing it before the reader is fed rather
than after. Scrubbed at the one point a log line becomes program data, via a
named allow-nothing list. `shopName` and `itemClassGUID` are deliberately kept:
they name a place and a thing, not a person, and they are most of what makes a
question answerable. Questions now read `playerId[<removed>]`.
