# Update - A4, the off switch

A4 done. The item the order says matters most.

One command: `venv\Scripts\python.exe scripts\takedown.py --yes`. It reads the
register for every CIG-sourced asset, moves each out of the built site into
`_to_delete/takedown_<stamp>/` (moved, not deleted - rule 1), stamps `removed`
on the record, and rebuilds.

The part that would have been easy to get wrong: `_deploy/models/` is NOT
regenerated by the build - a sync step populates it. Removing the file alone
would have lasted until the next sync put it back, and the site would quietly
serve withdrawn content again. So the stamp on the record is the durable half:
the build reads it, drops those ships out of the model map so no URL can be
built, and publishes them as `LOADOUT_WITHDRAWN`. If a withdrawn asset does
reappear, the build moves it out again and says so loudly - failing safe towards
removal rather than refusing to build, because a build that will not run is the
wrong behaviour in the middle of a takedown.

Degraded and honest: a withdrawn model is checked BEFORE the existing "no model
for this hull yet" case, because saying that about a ship whose model we removed
on purpose would be untrue. It gets its own sentence and the viewer is torn down
properly rather than left as a dead canvas.

The control RUNS the script as a subprocess against a fixture of 3 tagged and 4
untagged assets: tagged gone 3 of 3, UNTAGGED SURVIVED 4 of 4, real site still
builds. 19 assertions.

The untagged half was observed failing - a mutant that removed every registered
asset was caught with "0 of 4 survived". The dry run is proven by behaviour:
executed, then every file checked from the outside to still be there and the
register byte-identical. The control also restores the real repo and asserts the
restore (235 models back, LOADOUT_WITHDRAWN empty).

`docs/TAKEDOWN.md` leads with the command in a plain code block, the deploy step
second, and all explanation below both.
