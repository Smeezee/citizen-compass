## ONE PROOF CAME BACK GREEN FOR THE WRONG REASON AND I NEARLY BANKED IT

`imported_models:144` reported PROVEN on its first run. It had not reached 144.
I had seeded `imported_manifest.json`; the file is `import_manifest.json`, so it
fired at line 86 - a site already proved - and the exit code was right by
accident. Two other harness faults hid behind the same green: `node_modules`
lives in `checks/`, not the repo root, so playwright never resolved, and the
browsers path is derived from `HERE` too. Each of those failures produced a
non-2 exit that looked like an honest negative.

**Fixed by requiring three things, not one:** exit 2, the words NOT PERFORMED,
**and a string unique to the guard being aimed at.** Every line above meets all
three. This is the same shape as the `$(basename $f)` exit code that fooled me
last week - a green whose provenance was not checked.

## The one I could not prove, stated as not proven

`_verify_find_build_step.py:133` fires when the database holds no priced row in
`item_prices`. Reaching it needs **four full builds** and a database with that
table empty. Emptying the real one is a `DELETE FROM`, which rule 3 forbids
outside `run_e2e_test.py`. So the branch is unreachable for me to demonstrate -
**and it was equally undemonstrated before I touched it.**

What IS proven there: the `return 2` -> `sys.exit(main())` plumbing, which is the
same idiom proven working in `_verify_deploy_drift.py`, `_verify_rule16_labels.py`
and `_verify_version_single_source.py`. The mechanism is proven; the reachability
of that one branch is not, and I am not going to call that a pass.
