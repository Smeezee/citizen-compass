## 3. THE WATCHER WAS THE LIVE PRODUCER OF MIXED LINE ENDINGS

C1's ask was "fix the producer, not the product", and they were right that this
was the only one worth fixing. `appendUpdate` wrote a bare `"\n"` into
`_updates_log.md` **whose existing lines end `\r\n`** — every single time an
update was filed. The 12 CRLF-in-index files are latent; this one was live.

`existingEOL()` now reads what the file already uses and matches it.
**Matching, not normalising** — rewriting the log to one convention is a bulk
mutation to fix something that costs nothing today, which is the diff C1
explicitly refused.

**Three tests, and the second matters as much as the first:**

    TestAppendingToACRLFLogDoesNotMixEndings   the live defect
    TestAppendingToAnLFLogStaysLF             a writer that ALWAYS emitted CRLF
                                              would pass the first and be a new
                                              defect - the bulk rewrite refused
    TestANewLogIsLF                           a new file does not inherit the
                                              platform habit

**Proven in both directions.** Pre-fix behaviour: *"introduced 6 lone LF line
endings"*. Over-correction to always-CRLF: fails the LF test AND the new-log
test. Restored, `go vet` clean, rebuilt, deployed — PID 22192.

Log state before this update: `crlf=27165  lone_lf=19592`. This entry is the
